## Reproduction

From the worktree root, prepare the pinned Java 21 training classpath using `computer-player/training/prepare.ps1` on Windows or `computer-player/training/prepare.sh` on Linux. Set `FFB_STATE_SYNC_JAVA` to that JDK's Java executable. The database uses the pinned MariaDB 11.8.9 image in the measurement-only Compose file. The following PowerShell commands start a new isolated database, discover its assigned loopback port, and run the probes. Use fresh output directories for another run. Retain the sample JSON, JFR recordings and GC logs locally.

```powershell
$env:STATE_SYNC_DB_PASSWORD = [guid]::NewGuid().ToString('N')
$compose = 'tools/diagnostics/state-sync/compose.yaml'
docker compose -f $compose up -d --wait
$endpoint = docker compose -f $compose port database 3306
$env:STATE_SYNC_JDBC_URL = "jdbc:mariadb://$endpoint/ffb_state_sync_test"
node tools/diagnostics/capture-match-state-sync-fixtures.mjs --measure .tools/state-sync-g1
node tools/diagnostics/analyze-state-sync-move-timing.mjs .tools/state-sync-g1
$selected = '.tools/state-sync-g1/selected'
node tools/diagnostics/state-sync/run-storage.mjs $selected .tools/state-sync-storage measure
node tools/diagnostics/state-sync/storage-report.mjs $selected .tools/state-sync-storage
node tools/diagnostics/state-sync/run-full-time.mjs measure .tools/state-sync-full-time $selected
node tools/diagnostics/state-sync/run-full-time.mjs retained .tools/state-sync-retained $selected
```

The generator runs two 11-player rosters through Bogruk self-play with real server communication and rejects empty native logs or outcomes. The capture and move-timing commands supply journal cadence, native capture and per-copy statistics (items 6-8). The storage command supplies items 1-4, the prototype final write, baseline checkpoint/store, and items 9-11. The full-time commands measure production worker and post-release paths (items 4-6). The smoke mode also forces a single deferred completion. Production admission and task deadlines apply during the browser worker run.

## Findings for #611

The storage run used the corrected exporter; the worker trace used an earlier direct capture of the same decisions and seed. The worker appendix gives its exact input sizes. The reference match (Bogruk versus Bogruk, Human versus Orc, seed 43) reached full time at revision 929. Revision 50 had 153 logged commands and native outcomes. Revision 928 had 2,649 of each. The terminal checkpoint had 2,668. The machine ran Temurin 21.0.11+10 on an AMD Ryzen 7 260 with 31.3 GiB of host memory. Database trials used an isolated MariaDB 11.8.9 Compose project. Each timed JVM had a 768 MiB heap. G1 GC logs and JFR recordings stayed local.

1. **Checkpoint growth.** Decoded size rose from 2,540,478 to 43,025,921 bytes. The log, escaped events, transcript states and native outcomes, and request history explain 98.8% of the increase. Events and transcript states together added over 32 MB. See the field-by-field decoded/gzip comparison in the [storage appendix](../reviews/650-state-sync-storage.md). Fetching the current checkpoint still requires materializing this history even though it compresses well.
2. **Compact snapshot.** The prototype shrank from 91,336 to 86,294 decoded bytes, while independent gzip sizes went from 9,647 to 9,746. The log-free native engine also shrank from 53,061 to 47,854 bytes. This match falls below the 25% growth threshold. Test the missing continuation and cursor fields in the real implementation.
3. **Durable write and receipts.** Median journal append took 33.41 ms early and 36.93 ms late. Full checkpoint store took 77.89 and 843.43 ms. Indexed receipt lookup took 11.60 and 11.11 ms (medians, nine each). The storage appendix compares actual journal append and checkpoint replacement with the prototype's atomic snapshot/record/receipt/digest write. Receipt lookups include connection setup and use the same three-part index with 50 and 700 pre-existing entries.
4. **Restore.** The late baseline pays for JDBC read/decompression, checksum validation and native/session reconstruction before it can build a reply. The prototype reads one compressed current row and reconstructs the native game without replaying history. The late compact read/decode/native-restore medians were 18.10/1.09/16.27 ms (nine samples each). Building the late acting-coach view on the restored baseline still took a median 245.79 ms. Bringing down native restore time alone would leave considerable work before a coach receives a reply.
5. **Full time.** A normal final action from the late fixture failed to persist in all three attempts. Full-checkpoint materialization consumed 96-97% of the worker interval before a successful final SQL update. Cold active setup/load took 7.56 s at the median and reached 9.61 s. On the separately seeded terminal checkpoint, cold terminal setup/load took 11.43 s at the median and reached 13.11 s. It returned FULL_TIME with the result still pending. Six resident completion retries took 2.48-5.63 s each. Artifact construction accounted for 74-82% of their time. Neither the failed writes nor a missing phase is recorded as a zero-cost success. See the [full-time appendix](../reviews/650-state-sync-full-time.md) for queue, phase, SQL, GC and post-release measurements. A 2 s budget can expire during CPU and GC work before JDBC admission. These are single-match observations. The share of historical soak stalls caused by a particular match remains unknown.
6. **Compaction.** The byte threshold dominated the candidate run. The production policy typically compacted after about a dozen revisions, well before the 31-entry count threshold. The [move appendix](../reviews/650-state-sync-moves.md) gives measured cadence, entry sizes and fresh-JVM build timings. The storage appendix reports JDBC separately. A first-entry late delta exercises the journal write cost; the real terminal checkpoint path forces compaction.
7. **Native capture.** The move appendix reports native outcomes captured inside real accepted moves. Across three JVMs and 150 moves per window, native capture increased from 0.08135 ms to 0.10095 ms per move at p50 (1.24 times early). Preview copies dominated the long fixture moves.
8. **Preview copies.** Median time per block copy rose from 9.75 ms to 108.56 ms (11.13 times early), and median allocation from 5.33 MB to 64.28 MB (12.06 times). Total block-copy time per move rose 10.07-fold at p50. The 151 moves over 500 ms spent 97.51% of their combined time copying previews. For one matched copy, the storage appendix also compares log-inclusive and log-omitted native serialization/deserialization with skill registration on the same state. #652 had no published implementation PR with its own before/after measurements at review time. At the late checkpoint the paired experiment reduced one copy from 108.93 to 9.53 ms and from 56.63 to 2.15 MB allocated (medians, nine each).
9. **Patch, keyframe and existing replies.** The storage appendix reports patch and keyframe bytes alongside home, away and spectator output. The largest native result before the late checkpoint was a 22,357-byte halftime outcome at revision 486. Early and late ordinary patches measured 508 and 113 bytes. Their keyframes measured 13,511 and 13,616 bytes. Existing home/away replies were 31,583/31,186 bytes early and 25,361/26,404 late. A cadence decision needs the distribution of reconnect gaps and available tail memory.
10. **Parked coach.** Today a fallback reads and validates the full checkpoint before testing whether the human owes the decision. The synthetic training artifacts omit the human decision clock, which makes the existing `computerReply` decline its parked fast path. The prototype measures the compact-row read and a separate unchanged-revision reply, with a changed-revision probe falling back to snapshot bytes. A 33-byte late unchanged reply took a median 12.72 ms versus 22.58 ms for the changed-revision fallback to compact bytes (nine samples each). A usable summary also needs the maintenance and clock inputs from decision 18.
11. **Worker cost.** Ordinary, keyframe and rare moves have separate groups in the storage appendix. Across 102 samples per group, the early/late whole-task p99 was 33.50/33.15 ms for ordinary moves and 41.42/31.33 ms for keyframes. Late median cost was 0.95 times early for ordinary moves and 0.98 times early for keyframes. Both active cohorts stayed below 100 ms at p99. End-to-end ADR 0006 compliance remains inconclusive because the probe starts from projected engine state and uses in-memory recipients. The 2,000 ms request ceiling is separate and failed on the exercised late production path.

The training engine runs legal decisions without the browser application's admission ceiling. The 41.02 MiB late checkpoint lies above the 40 MiB append reserve and below the 44 MiB decoded cap. A persisted match can size-stop earlier. The late baseline deliberately exposes that boundary; a successful short-match completion cannot establish the cost of a durable terminal write at this size.

## Proposed targets for maintainer review

| Operation | Proposed target | Evidence and decision |
| --- | --- | --- |
| Atomic move write | p99 at most 60 ms | Early/late ordinary writes measured 30.74/32.74 ms at p99. Keyframes measured 40.52/30.19 ms. This leaves a portion of the 100 ms worker budget for publishing and engine work. |
| Active compact restore | p90 at most 60 ms through native reconstruction, with role-view construction measured separately | The late read, decode and native restore together measured 35.44 ms at p50 and 50.05 ms at p90, paired by repetition. Nine samples leave p99 inconclusive. |
| Projection and five-recipient delivery | p99 at most 5 ms after subtracting the commit from the same task | The measured p99 was 3.06/0.65 ms early/late on ordinary moves and 1.88/1.54 ms on keyframes. Include authorization, socket dispatch and missing projection fields before adopting this in production. |
| Full-time worker | Retain 100 ms p99 as the acceptance target | The sealed write took 29.35 ms (ordinary) and 47.66 ms (keyframe) at p99. Whole-task p99 was 30.51 and 48.54 ms. Each group had 102 samples. Median terminal DB connect plus SELECT 1 was 10.18 ms, maximum 12.80 across nine samples. |

The initial same-row write experiment peaked at 160.66/163.33 ms p99 for ordinary/keyframe sealed writes, and browser validation overlapped the slowest JVM. The final run used the penultimate blob as the terminal predecessor and ran after concurrent validation and training ended. The uncontended sealed write stayed below 100 ms at p99. The earlier tail shows why representative host load belongs in the maintainer’s decision on the terminal transaction. The 2,000 ms ceiling remains a separate request safety check.

## What each timing includes

The worker trace records both queue lanes at dequeue, queue wait separately from execution, and exclusive method times within the same attempt. It follows the terminal checkpoint, event materialization and parsing, transcript and chat materialization, canonical serialization, validation, `MatchJson.storageText`, compression, connection open, SQL update and commit. It follows release into live-transcript delivery and the stored-row read, decode and transcript rebuild. Later human `setup/load` attempts and control tasks have separate records, including retained-checkpoint reconstruction, completed artifact comparison and retained-concession paths when reached. The existing SQL spans cover the recovery repository. Prepared-match connection, update and commit timings come from the test-only JDBC probe. The test agent observes the actual calls, including tasks without a browser request ID.

The prototype starts with decoded captured state. It removes historical arrays, retains native continuation and dice state, and records transcript/chat counters and the drive tracker projection. It does not implement a production restore format, a standalone unfinished-movement cursor, replay validation or new clock semantics. Compact restore measures fetching compressed bytes, decoding the snapshot, and native `initFrom`. Rebuilding role views is sampled on the restored baseline session because there is no compact session deserializer.

The prototype transaction opens a real connection, locks the current row at the expected generation, compresses and replaces the snapshot, advances the SHA-256 chain, inserts a replay record and indexed receipt, and commits. Full-time samples also mark the row sealed and store the result. Receipts are synthetic and seeded to 50 or 700 before the lookup. Repetitions update the same logical revision with a fixed-width predecessor digest. The active-row fixture uses the previous revision number to vary the compressed blob. The sealed write starts with the actual penultimate snapshot. They exclude construction of the compact JSON string and a complete history audit. Recovery repository append and checkpoint replacement use the real codec, SQL, connection and transaction implementation.

The prototype sends a whole-player / whole-section patch to two coaches and three spectators. The role owning the turn receives its actions. The timed prototype task includes public projection from transcript state, encoding, durable commit and copying the envelopes to in-memory recipients on one worker. It excludes rules execution, authorization, network/backpressure, browser rendering, private forecast construction, and complete report/animation coverage and historical actor-only pass-range and Kick projections. A keyframe sample sends both patch and keyframe. The rare case uses the largest native-outcome array observed up to the checkpoint and the cohort's compact row to isolate record size. Baseline per-role sizes are application JSON, before WebSocket framing. Equal-revision and changed-revision row probes isolate summary lookup and the unchanged reply versus falling back to snapshot bytes. Production also checks inactivity, pending work, reactive decisions and retention. Those eligibility checks need testing on the final format.

## Validation

The diagnostics CLI tests independently mutate the analyzer and helper, verify LF/CRLF equality, and exercise both historical p95 policies. CI runs the fingerprint test. Reprocessing `.tools/history-scaling-20261108-final` produced byte-identical JSON and Markdown history-scaling reports. Their SHA-256 digests were `716411222d30f3286376b2138ccd02e37480290fbd43e691e1de990a54fb2d22` and `44baf51bb3e5a964cdedf9ec92628e0f351c4a32958afac9e80e55604a998f5e`. After the review fixes, all 12 diagnostics tests, 98 computer-player tests, 594 browser tests, and 22 focused server tests passed. TypeScript and Vite built successfully. The focused Maven selector was `StateSyncProjectionTest,TrainingEngineHostTest,BrowserRequestTimingTest`. Seed 44 retained a complete per-move trace but failed during terminal artifact export in an earlier harness build. Its recovered JFR recording covers both timing windows; seeds 43 and 45 supplied verified full exports after the fix.
